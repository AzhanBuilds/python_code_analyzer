# PRODUCT REQUIREMENTS DOCUMENT (PRD)
# Python Code Analyzer

**Project Name:** Python Code Analyzer  
**Product Type:** Full-stack web application  
**Frontend:** React + Vite + JavaScript + Tailwind CSS  
**Backend:** Python + Flask  
**Static Analysis Engine:** Python AST, `tokenize`, `ast` and custom rule engine  
**Development Environment:** Google Antigravity  
**Version:** 1.0  
**Priority:** Build a complete, functional, secure, responsive application  
**Primary Constraint:** Never execute user-submitted Python code.

---

# 1. PROJECT OVERVIEW

## 1.1 Project Description

Build a professional web-based Python Code Analyzer that allows users to enter or paste Python source code into an editor and analyze it without executing it.

The application must inspect the submitted source code and generate a detailed analysis report containing:

- Code quality score out of 100.
- Total number of source lines.
- Function count.
- Class count.
- Import count.
- Loop count.
- Condition count.
- Comment count.
- Cyclomatic complexity.
- Warnings with severity and line numbers.
- Actionable code improvement suggestions.
- TODO/FIXME comment detection.
- Python syntax error diagnostics.
- A clear and organized analysis results dashboard.

The interface should look like a modern developer tool, with a source-code editor on the left and analysis results on the right on desktop screens, adapting to a stacked layout on smaller devices.

This must be a real, working full-stack application, not a static mockup or a frontend-only prototype.

## 1.2 Main Objective

Create an application where users can submit Python code, click **Analyze Code**, and receive accurate static-analysis results generated by the Flask backend.

The frontend must communicate with the backend through a real REST API. The backend must calculate metrics and findings dynamically from the submitted source code.

Do not hardcode the example results in this document into the application.

## 1.3 Core Product Principles

1. Analyze source code without running it.
2. Calculate metrics from the actual submitted code.
3. Provide understandable and actionable findings.
4. Show precise source line numbers whenever possible.
5. Maintain a professional, consistent UI.
6. Keep frontend and backend responsibilities separate.
7. Validate input and handle errors gracefully.
8. Make the application easy to install, run, test and extend.
9. Preserve existing project functionality if a codebase already exists.
10. Never replace working project files without first inspecting them.

## 7.3 Code Metrics

Display the following metrics:

| Metric | Meaning |
|---|---|
| Total Lines | Number of physical source lines |
| Functions | Number of function and asynchronous-function definitions |
| Classes | Number of class definitions |
| Imports | Number of import statements |
| Loops | Number of `for`, `async for` and `while` loop nodes |
| Conditions | Number of `if` and conditional-expression nodes |
| Comments | Number of comment tokens, excluding `#` inside string literals |
| Cyclomatic Complexity | Documented aggregate complexity metric |

The example result may show:

- 6 Total lines
- 0 Functions
- 0 Classes
- 0 Imports
- 0 Loops
- 0 Conditions
- 2 Comments
- 1 Cyclomatic complexity

These are illustrative values, not default values.

### Metric Definitions

**Total Lines**

Count physical source lines consistently. Document the treatment of empty input and trailing newlines.

**Functions**

Count `FunctionDef` and `AsyncFunctionDef` nodes.

**Classes**

Count `ClassDef` nodes.

**Imports**

Count import statements, not imported names. One `import os, sys` statement counts as one statement; one `from pathlib import Path` statement counts as one statement.

**Loops**

Count `For`, `AsyncFor` and `While` AST nodes.

**Conditions**

Count `If` and `IfExp` AST nodes. If the implementation counts other decision constructs, document them explicitly.

**Comments**

Use Python tokenization so that a hash character inside a string does not count as a comment.

**Cyclomatic Complexity**

Calculate a documented complexity value.

For the initial implementation, calculate per-function complexity as 1 plus the number of decision points in that function. Decision points include `if`, `for`, `async for`, `while`, conditional expressions, `except` handlers and Boolean operators according to the chosen convention.

For top-level code, use an explicitly documented module-level complexity value.

Display the aggregate as the sum of module-level and function-level complexities. For a valid, nonempty program with no decisions, the aggregate should be 1 under this convention.

Nested function bodies must not accidentally be counted twice when calculating an enclosing function's complexity.

# 9. STATIC-ANALYSIS ENGINE

## 9.1 Core Principle

The backend must inspect source code as data.

It must not call:

- `exec()`.
- `eval()`.
- `subprocess` to run the submitted code.
- A shell to execute the submitted code.
- An interpreter to execute the submitted code.
- Any equivalent execution mechanism.

Do not import the submitted source as a Python module.

Do not execute code while calculating metrics, generating warnings or testing the analyzer.

Use AST parsing, tokenization, source-text inspection and carefully defined static rules.

## 9.2 Syntax Analysis

Use `ast.parse()` to parse valid source text.

When parsing fails, return a structured syntax error containing:

- Error message.
- Line number when available.
- Column number when available.
- Error category.

Example:

```json
{
  "status": "syntax_error",
  "syntax_error": {
    "message": "invalid syntax",
    "line": 3,
    "column": 12
  },
  "metrics": null,
  "quality_score": null,
  "warnings": [],
  "suggestions": [],
  "todos": [],
  "fixmes": []
}
```

This is a response-shape example; actual messages and positions must come from the parser.

Do not attempt to fabricate metrics that depend on a successful AST parse.

Independent token-based diagnostics may be returned if their validity is preserved, but the UI must distinguish them from complete analysis results.

## 9.3 Required Analysis Rules

Implement a modular rule engine.

At minimum, include the following rules where applicable.

### Rule 1: Print Usage

Rule ID: `print-usage`

Detect calls to the built-in `print()` function where the analyzer can identify them reliably.

Default severity: Low.

Example message:

`print() is used in the code.`

Suggested recommendation:

`Use a logger instead of print() for application output.`

Do not flag calls that can be statically identified as references to a locally defined or imported function named `print`, unless the rule explicitly documents a conservative limitation.

### Rule 2: Long Lines

Rule ID: `line-too-long`

Detect physical source lines exceeding a configurable maximum length.

Suggested default: 100 characters.

Include the line number and actual line length.

### Rule 3: Missing Function Docstring

Rule ID: `missing-function-docstring`

Detect functions that do not contain a docstring, according to Python's AST docstring semantics.

Allow the rule to be configurable because not every small function requires a docstring.

### Rule 4: Missing Class Docstring

Rule ID: `missing-class-docstring`

Detect classes without a docstring, using AST-based detection.

### Rule 5: Excessive Function Length

Rule ID: `function-too-long`

Detect functions exceeding a configurable number of physical source lines.

Suggested initial threshold: 50 lines.

### Rule 6: Bare Except

Rule ID: `bare-except`

Detect bare `except:` handlers.

Explain that catching specific exceptions is generally preferable.

### Rule 7: Unused Imports

Rule ID: `unused-import`

Implement a conservative static check.

Do not remove or automatically flag imports when the analyzer cannot determine their use reliably. Document limitations involving aliases, wildcard imports, re-exports and dynamic behavior.

### Rule 8: TODO/FIXME

Rule IDs:

- `todo-comment`
- `fixme-comment`

Detect markers in comment tokens and report each matching line.

### Rule 9: High Complexity

Rule ID: `high-complexity`

Detect functions whose calculated complexity exceeds a configurable threshold.

Suggested starting threshold: 10.

Use the same complexity calculation for both metrics and findings.

### Rule 10: Undefined Names

Rule ID: `undefined-name`

Only implement this rule if the analyzer can handle Python scopes and bindings with reasonable accuracy.

Account for:

- Function-local names.
- Parameters.
- Global declarations.
- Nonlocal declarations.
- Imports.
- Built-ins.
- Comprehension scopes.
- Class scopes.
- Exception targets.
- Assignment expressions.

Do not report a name as undefined merely because it is absent from a simple list of assignments.

If reliable scope analysis cannot be implemented within the initial scope, leave this rule disabled and document it as a future improvement rather than generating misleading warnings.

## 9.4 Rule Engine Output

Every finding should use a consistent internal structure.

Example:

```json
{
  "rule_id": "print-usage",
  "severity": "low",
  "line": 5,
  "column": 1,
  "message": "print() is used in the code.",
  "suggestion": "Use a logger instead of print() for application output."
}
```

A warning and suggestion can share a rule identifier when appropriate.

The rule engine should define:

- Rule identifier.
- Detection condition.
- Severity.
- Message template.
- Optional suggestion.
- Scoring impact.
- Whether it produces a warning, suggestion or both.

Avoid duplicate findings for the same rule and source location unless duplicates are meaningful and documented.

# 10. QUALITY SCORE CALCULATION

## 10.1 Requirements

Create a dedicated scoring module.

The score must:

- Be an integer between 0 and 100.
- Be based on detected findings and documented weights.
- Be deterministic for identical source and configuration.
- Never be a random or hardcoded number.
- Be reproducible in tests.
- Use the same rule classifications as the findings dashboard.

## 10.2 Suggested Initial Scoring Model

Start with 100 points.

Subtract configured penalties for findings, for example:

| Severity | Illustrative penalty |
|---|---:|
| Critical | 20 |
| High | 10 |
| Medium | 5 |
| Low | 2 |
| Info | 0 |

Use these as configurable initial defaults, not immutable rules.

Prevent excessive deductions from producing a negative score.

Clamp the result between 0 and 100.

Deduplicate findings before scoring if they represent the same underlying issue.

Do not penalize a finding twice merely because the UI displays it as both a warning and a related suggestion.

Document whether repeated findings of the same rule can each affect the score.

Do not silently change the scoring model between analyses.

## 10.3 Score Interpretation

Use these initial display ranges:

- 90â€“100: Excellent.
- 75â€“89: Good.
- 60â€“74: Needs improvement.
- 0â€“59: Poor.

These labels are user-interface guidance, not a claim that a score universally measures program correctness.

## 10.4 Syntax Errors

If syntax parsing fails, do not display an apparently valid quality score based on incomplete AST analysis.

Return `null` for the score and unavailable AST metrics, and clearly communicate why.

# 12. BACKEND API SPECIFICATION

## 12.1 Analysis Endpoint

Endpoint:

`POST /api/analyze`

Content type:

`application/json`

Request body:

```json
{
  "code": "def add(a, b):\n    return a + b\n"
}
```

The `code` field must be a string.

## 12.2 Successful Response

Example response structure:

```json
{
  "status": "success",
  "quality_score": 100,
  "metrics": {
    "total_lines": 2,
    "functions": 1,
    "classes": 0,
    "imports": 0,
    "loops": 0,
    "conditions": 0,
    "comments": 0,
    "cyclomatic_complexity": 1
  },
  "warnings": [],
  "suggestions": [],
  "todos": [],
  "fixmes": [],
  "summary": {
    "warning_count": 0,
    "suggestion_count": 0,
    "todo_count": 0,
    "fixme_count": 0
  }
}
```

This is an illustrative schema. The implementation must calculate every value from the request.

The example score is not a requirement that all code without warnings receive 100. It depends on the documented scoring model.

## 12.3 Validation Errors

Return HTTP 400 for invalid request structures, such as:

- Missing `code`.
- `code` is not a string.
- Malformed JSON.

Return HTTP 413 if the source exceeds the configured size limit.

Suggested initial source limit: 100,000 characters. Make it configurable.

Return HTTP 429 if rate limiting is enabled and the limit is exceeded.

Return HTTP 500 for unexpected server failures without exposing stack traces or secrets to the client.

## 12.4 Health Endpoint

Implement:

`GET /api/health`

Example:

```json
{
  "status": "ok",
  "service": "python-code-analyzer"
}
```

The health endpoint must report application availability without running user code.

## 12.5 CORS

Configure CORS only for the required frontend origin in development and production.

Do not allow every origin in production without an explicit security justification.

## 12.6 API Consistency

- Use consistent response keys.
- Return numeric metrics as numbers.
- Return finding collections as arrays.
- Return unavailable values as `null`, not misleading zeroes.
- Do not return HTML error pages to the React application.
- Do not expose Python tracebacks.
- Validate every request on the server even if the frontend already validates it.

# 13. FRONTEND AND BACKEND INTEGRATION

## 13.1 Request Flow

Implement this flow:

1. The user edits Python code.
2. The user clicks Analyze Code.
3. React validates basic input.
4. The frontend sends `POST /api/analyze`.
5. Flask validates the request.
6. The analyzer parses and inspects the source.
7. The backend calculates metrics.
8. The backend runs the configured static-analysis rules.
9. The backend detects TODO/FIXME comments.
10. The backend calculates the quality score when analysis is valid.
11. Flask returns structured JSON.
12. React updates the results panel.
13. The UI displays findings and metrics.

At no point should the submitted source be executed.

## 13.2 Environment Configuration

Use environment variables for configurable API addresses and deployment settings.

For Vite, use an appropriate public frontend environment variable such as:

`VITE_API_BASE_URL`

Do not place secrets in Vite environment variables because frontend variables are exposed to the browser.

Provide a development default that works with the local Flask server, and document how to configure production deployment.

## 13.3 Error Handling

Implement user-friendly messages for:

- Backend unavailable.
- Request timeout.
- Invalid API response.
- Invalid input.
- Source too large.
- Syntax error.
- Unexpected analysis failure.

Do not erase the user's source code when an API request fails.

Do not display raw server stack traces in the UI.

## 13.4 Stale Request Handling

If the user submits multiple analyses, ensure that an older response cannot overwrite the result for newer source code.

Use request cancellation or a request identifier where appropriate.

# 16. SECURITY REQUIREMENTS

Security is mandatory.

## 16.1 Never Execute User Code

The application must only inspect submitted source text.

Do not use `exec`, `eval`, dynamic imports, shell commands or subprocess execution to analyze submitted Python code.

Do not import submitted source modules.

Do not use an external execution service.

Do not run submitted code as part of the test suite.

## 16.2 Input Validation

- Require a JSON object.
- Validate the `code` field type.
- Apply a configurable source-size limit.
- Reject malformed requests safely.
- Handle invalid Unicode or decoding conditions appropriately.
- Prevent excessively large source inputs from causing uncontrolled memory consumption.

## 16.3 Resource Protection

- Set sensible request timeouts.
- Configure rate limiting where appropriate.
- Avoid pathological regular expressions.
- Avoid expensive repeated full-source scans.
- Restrict concurrent analysis workloads if necessary.
- Keep analysis algorithms predictable.

## 16.4 Data Privacy

- Do not log complete source code by default.
- Do not transmit source code to third-party AI services.
- Do not store source code without a clear feature requirement and user-facing disclosure.
- Do not place source code or secrets in error logs.
- Do not include submitted source in health-check responses.

## 16.5 Frontend Safety

Render code and finding messages as text, not unsanitized HTML.

Do not use `dangerouslySetInnerHTML` to display source code or analyzer output.

## 16.6 Production Security

- Use HTTPS in production.
- Store secrets in environment variables.
- Restrict CORS.
- Disable debug mode in production.
- Return generic server error messages.
- Keep dependencies reasonably current.
- Avoid exposing server paths or sensitive configuration.
